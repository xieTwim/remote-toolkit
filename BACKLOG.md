# remote-toolkit — open problems

One line per real open problem: `- <problem> → <fix idea> (<date>, <where seen>)`. Delete the line when it
is fixed; git keeps the history. Incidents go to `~/Work/Harness/FRICTION.md` first.

- A synced tree lands on the remote with Mutagen's portable defaults (files 0600, directories and executables 0700), so a remote process running as another uid gets EACCES → an opt-in per-profile default file and directory mode at session create, documented beside the note that session options freeze at create (2026-10-18).
- The first apply of a small changed file can fail on the remote with `unable to set staged file permissions … no such file or directory` and stay stuck in staging (four times on one profile, four more on another on 2026-11-14..16, where `mutagen sync flush` did land it; pause/resume did not clear it) → find what removes the beta staging file between stage and apply; until then, compare the remote digest before launching (2026-10-11; twice more 2026-10-24 and 10-29 on one profile, where `mutagen sync flush` landed the file at once).
- Launchers outside `rt` can start before synced files arrive, and live edits can change code under a running analysis → integrate the existing `rt verify <paths>` digest check into those launchers and run long reads from a frozen copy; `verify` itself is implemented and regression-tested (2026-10-19, two incidents in one research project; implementation confirmed 2026-10-26). A flush is no barrier either: `rt flush` gave up after 90 s while Mutagen sat in Scanning files, and a digest read just after `mutagen sync flush` returned was still the old file, the new one landing 4 s later mid-run → a flush that takes the paths it must land and returns only once `verify` passes (2026-10-25 and 10-29, the same project).
- The documented way to apply an ignore change, `rt disconnect && rt connect`, recreates the session with no common ancestor, so every file that differs between the sides is a conflict that `two-way-resolved` hands to the LOCAL side: a finished remote job log was silently overwritten by a stale local copy (SKILL.md warns beside the recipe) → before `_sync_create` on a non-empty local replica, name the files a recreate would overwrite and refuse or warn, or start the recreate one-way from the remote and flip to two-way after the first cycle (which: owner's call) (2026-10-18, one research project).
- Sessions created before 2249020 from a scalar `MUTAGEN_IGNORE` still enforce it as one dead pattern (two live ones on one machine as of 2026-10-19; `rt sync status` printing the whole string on one line is the tell) → recreate each at a quiet moment, minding the recreate line above (2026-10-19, one research project).
- With umask 0777, push creates an unreadable staging file and reports a digest mismatch before installation → stage with private read/write permissions, then apply the intended final mode; reproduce separately before changing staging behaviour (2026-10-29, local permission regression fixture).
- Across the ssh hop: `rt exec -- bash -c '<a; b>'` loses its outer quotes (the words are joined into one string for the remote shell, as ssh itself does), an until-loop on `rt exec "grep -q …"` ended at once, and `exec "cat <file>"` returned a copy one byte longer → pin each with a canary before changing anything (2026-11-07..11, three reports).
- `pgrep -f`/`pkill -f` sent over ssh match the remote wrapper shell whose command line holds the pattern: a wait loop never ended and a rented box billed ~10.5 h idle, a kill took the exec with it (exit 143/255, output lost); SKILL.md has warned since 2026-09-13 and it still bit four times → have `rt exec` hand the remote shell its text so it is not in any process's argv (e.g. base64 decoded into `eval`, or the script on a file), with a canary that a `pgrep -f <own text>` finds nothing; a transport change beside the quoting line above, so owner's call (2026-11-14..19, three research projects: twice over plain ssh, three times over kubectl exec, once locally).
- An allocation that lands more than RT_COLAB_ADOPT_WAIT (10 min) after `colab new` gave up still bills with no record and no watchdog (rt now takes over earlier ones by the request's notebook hash) → keep the hashes of recent failed requests and let `rt colab ls` ask by them too (2026-11-24, upstream google-colab-cli#263 and discussion #141; not seen here).
- On the next google-colab-cli upgrade (pinned 0.8.0): the bridge could drop the hidden `--colab-internal-mode cmd` for bare `colab --config <json> ssh --proxy-mode`, which the CLI documents as resolve-only and which the one-session `--config` makes unambiguous (it lists assignments on each new connection; check it live), and `_colab_heal_slot` could call the upcoming `colab ssh --force`, or go entirely if the backend fix its maintainers plan lands (2026-11-24, upstream docs and PR #254).
