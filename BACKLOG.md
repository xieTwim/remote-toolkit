# remote-toolkit — open problems

One line per real open problem: `- <problem> → <fix idea> (<date>, <where seen>)`. Delete the line when it
is fixed; git keeps the history. Incidents go to `~/Work/Harness/FRICTION.md` first.

- A synced tree lands on the remote with Mutagen's portable defaults (files 0600, directories and executables 0700), so a remote process running as another uid gets EACCES → an opt-in per-profile default file and directory mode at session create, documented beside the note that session options freeze at create (2026-10-18).
- The first apply of a small changed file can fail on the remote with `unable to set staged file permissions … no such file or directory` and stay stuck in staging (four times on one profile; flush and pause/resume did not clear it) → find what removes the beta staging file between stage and apply; until then, compare the remote digest before launching (2026-10-11; twice more 2026-10-24 and 10-29 on one profile, where `mutagen sync flush` landed the file at once).
- Launchers outside `rt` can start before synced files arrive, and live edits can change code under a running analysis → integrate the existing `rt verify <paths>` digest check into those launchers and run long reads from a frozen copy; `verify` itself is implemented and regression-tested (2026-10-19, two incidents in one research project; implementation confirmed 2026-10-26). A flush is no barrier either: `rt flush` gave up after 90 s while Mutagen sat in Scanning files, and a digest read just after `mutagen sync flush` returned was still the old file, the new one landing 4 s later mid-run → a flush that takes the paths it must land and returns only once `verify` passes (2026-10-25 and 10-29, the same project).
- `rt push` of a NEW file sets its remote mode to `--w------T` (owner write-only + sticky) while the local file is 0644 and the remote umask 022; a push that replaces a file keeps its mode. Four JSON files sat unreadable for 8 h and a Slurm job died on PermissionError mid-pipeline → likely a decimal `stat` mode applied as octal (0644 → 0o1204): parse the local mode as octal, apply it under the remote umask, and have `rt push` stat the result and refuse a mode without owner read; until then `chmod 644` after a first push (2026-10-22, one research project).
- The documented way to apply an ignore change, `rt disconnect && rt connect`, recreates the session with no common ancestor, so every file that differs between the sides is a conflict that `two-way-resolved` hands to the LOCAL side: a finished remote job log was silently overwritten by a stale local copy (SKILL.md warns beside the recipe) → before `_sync_create` on a non-empty local replica, name the files a recreate would overwrite and refuse or warn, or start the recreate one-way from the remote and flip to two-way after the first cycle (which: owner's call) (2026-10-18, one research project).
- Sessions created before 2249020 from a scalar `MUTAGEN_IGNORE` still enforce it as one dead pattern (two live ones on one machine as of 2026-10-19; `rt sync status` printing the whole string on one line is the tell) → recreate each at a quiet moment, minding the recreate line above (2026-10-19, one research project).
