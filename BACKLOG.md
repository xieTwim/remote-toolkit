- [fixed remote-toolkit@69be333] 2026-08-06 train-stab: **`exec` truncates a large remote stdout silently and still exits 0** — the lane's own shape, on the output path. A command whose stdout exceeds roughly 100KB comes back cut off, with no marker in the stream and no non-zero status, so a caller that pipes several files through one `exec` receives a partial payload that parses as a complete one. Measured: a multi-file pull returned 1 of 7 files and reported success; the loss was caught only because the caller happened to hold a manifest of what it had asked for. **Same failure CONDITION as a cross-repo record from 2026-07-13 (`rt exec` losing 6 of 7 files): one pattern, two occurrences, three weeks apart.** Closed as the entry itself split it — the additive half only.
  **Where the cap is NOT, established by reading the path rather than by measuring a symptom: there is no cap in `rt`, and `ssh` does not truncate.** `_exec_sync` inherited its stdout straight through. So the ~100KB cut is in whatever CAPTURES rt's stdout — an agent's tool-output limit, a harness buffer — and `rt` can neither see nor prevent it. That is why the fix is two assertions and not a bigger buffer: the remote shell now writes a TRAILER to stderr after the command exits (a per-invocation nonce token plus the command's status), so a stream that ends without it is reported `output is TRUNCATED` and exits **125** — "no outcome established", beside the 124 already used for the bound, and a real transport status is never replaced by it. And the payload is COUNTED on the way through, with a complete one at or above 64 KiB (`RT_EXEC_REPORT_BYTES`) reporting its size, which is the number a caller compares against what it actually holds. Below the threshold nothing is printed: a small output behaves exactly as before. stdout stays a byte-exact pass-through, and that is load-bearing rather than tidy — a live caller pipes `tar cf -` through `exec` into `tar xf -`, so the trailer had to go on stderr (filtered back out by a nonce-matching awk) and the count had to be taken by `tee`/`wc` over a fifo rather than by any line-oriented filter. Pinned by a NUL-byte, no-trailing-newline payload.
  **Consumers counted before touching the status set** (`rg --no-ignore`, 2026-08-07): 405 static occurrences in 168 files across 83 directories, but that is the MENTION count and it is the wrong predicate — the decision changes an exit status, so the predicate is *who branches on it*. Excluding prose, notes and captured transcripts leaves **four real script callers, and not one branches on `rt exec`'s status**: every one pipes stdout into `tar`/`grep`/`awk`, which discards it. So 125 breaks nobody, and — the half worth writing down — helps nobody either without the follow-up entry above.
  **Two defects in this fix were found by attacking it, not by the suite, and both are the shape the fix is about.** (1) Waiting for the accounting readers reinstated an UNBOUNDED wait: they see EOF only when every holder of the payload pipe closes it, which after `--timeout` kills ssh can include something ssh left behind — a 1s bound returned after 4s. `_exec_reap` bounds that wait at 2s and then kills, and because `wc` writes its total only at EOF the count is then reported as unestablished, never as 0. (2) The trailer proves the COMMAND wrote everything it had and says nothing about whether `rt` handed it all on: `exec 'cat 400KB' | head -c 5` reported *"81920 bytes of stdout, complete"* — the same unsupported benign claim, reintroduced one layer out. The pass-through's own status is now a third input, and a consumer that closed early is reported as a PREFIX with a non-zero status even when the command exited 0. Note the boundary that check had to find: at 70 KB the defect does not reproduce, because every byte still reaches rt's stdout and the kernel buffers it — the claim only becomes rt's to get wrong once forwarding itself cannot finish. A third, smaller correction came from a mutation run on this commit's own comment: the wrapper's trailing `exit $?` was described as what keeps `exec`'s status the command's, and it is not — the status is read out of the trailer, and removing that line left the suite green. It is kept for the narrower reason now written beside it.

- [fixed remote-toolkit@67a8df8] 2026-08-01 dllm-reasoning: nothing told a caller when a staged file had actually ARRIVED, so callers waited a fixed sleep and then installed a stale copy. Measured: a patched launcher script was staged, waited on for ten seconds, and the still-stale remote copy was copied into place — `bash -n` passed because the OLD file is valid shell, so the run started and died instantly on an unknown case, holding 8 GPUs idle for ~25 minutes. **[RULED 2026-08-05, human, decisions §5.3] THE ARRIVAL ASSERTION ONLY** — the per-run staging wrapper stays a separate project (register §3.3), and this fix does not touch it. `rt verify [--timeout N] [--interval N] <path>...` hashes the named paths locally, has the remote hash the same paths, and compares whole manifests, polling until they agree. The local side is recomputed AFTER the remote answer, so a file edited during the check is not certified — the contract is "equality was observed and held across the check", not "these bytes are frozen", which nothing here could promise. Verified end-to-end against a real remote: staged edit → rc 3 naming the differing file with both digests → wait → rc 0 → remote confirmed to hold the new bytes

- [fixed remote-toolkit@fc02cb5] 2026-08-01 grpo-speed: bounded reads through `exec` failed on macOS with "command not found: timeout" — the GNU binary is not present on darwin (it is `gtimeout`, from coreutils) and callers wrote `timeout N rt … exec …`. - [fixed remote-toolkit@b9e35f8] 2026-08-02 a background job's recorded exit status was `tee`'s, not the command's. `{ cmd; } 2>&1 | tee log; echo "EXIT_CODE=$?"` records the LAST element of the pipeline, and `tee` essentially always succeeds — so every job that ever started was recorded `EXIT_CODE=0` and listed by `rt logs` as `[DONE]`, including one that died on its first line. A caller reading that list to decide whether a run finished was told yes, always. Fixed with a POSIX marker file (`${PIPESTATUS[0]}` is bash-only and tmux starts the remote LOGIN shell, so on a dash host it would expand to nothing — the same class of silent failure). The command runs in an explicit subshell so that a literal `exit N` cannot terminate the pipeline's own subshell before the marker is written. `rt` got its first tests with this: `test/canary_rt.sh` sources `rt`, stubs `_ssh`, and RUNS the captured remote command locally, so the four failure shapes are pinned by behaviour rather than by wording

- [fixed remote-toolkit@4a4b376] 2026-08-02 a failed flush was converted into a successful CLI call — and the reason the tool held two OPPOSITE policies for it (`exec` ran anyway, `slurm submit` aborted) is that "flush failed" was one word for two states. `_sync_flush` now returns 2 (paused / mutagen error — nothing synchronised) or 3 (the time bound elapsed; the daemon is still working). `exec` refuses on 2 and continues loudly on 3, because refusing on a routine timeout would make `--no-flush` habitual and turn the protection off entirely; `slurm submit` refuses on both, since a queued job outlives the shell; `sync flush` exits non-zero. **Human ruling 2026-08-02** — the two states had to be separated before any single policy could be right

- [fixed remote-toolkit@1a309cf,36adcb5] 2026-08-02 **an unhealthy sync session was classified `active`.** The classifier had no negative case: anything carrying `Identifier:` that did not match `Status:.*Paused` and did not match `Connected: No` was called healthy, so every state Mutagen has that those two strings do not name reported as healthy. The one that actually happens is the entry-count circuit breaker, which reports `Connected: Yes` on BOTH endpoints with `Status: Waiting … for rescan`. Re-confirmed against real Mutagen 0.18.1 2026-08-05. `_sync_status` now classifies from a structured `mutagen sync list --template` probe of `.Paused` / `.Status` / `.LastError` / `.Alpha.Connected` / `.Beta.Connected`, and the classification is **POSITIVE**: `active` requires a status verb on a recognised-healthy list, so a verb this tool does not know (a future Mutagen adding a brake) reports `unknown` loudly instead of rejoining `active` silently. Seven states rather than four; the new ones are `erroring` (a live error — measured NOT sticky, it clears within one rescan interval once the condition clears, so it is a live condition and not a scar; the entry-count breaker lives here), `halted` (one of Mutagen's three SAFETY BRAKES) and **`unknown`** (the daemon could not be asked, or two sessions matched one profile's labels — previously encoded as `none`, i.e. "there is no sync session", a claim about the remote that nothing established). **The first version of this fix keyed on `.LastError` alone and an independent review refuted it**: measured 2026-08-05 by driving each condition, all three of `HaltedOnRootEmptied` / `HaltedOnRootDeletion` / `HaltedOnRootTypeChange` report an **EMPTY** `.LastError` with **both endpoints `Connected: true`**, so an error-only classifier called all three healthy — the same defect this entry is about, one state over. The entry's own fix shape said "classify on `Last error:` **and on the status verb**"; only half of it had been implemented. `halted` and `erroring` are separate states because the REMEDY differs: an `erroring` session is fixed by repairing the ignore list and recreating, while recreating a `halted` one would silently decide which side's contents win, so its message points at `mutagen sync reset` instead. Two consequences were larger than the classification itself: (a) measured 2026-08-05, a flush against a halted session does not fail, it **HANGS** — still running after 15s — so it used to burn `RT_FLUSH_TIMEOUT` and return **3**, "the daemon is still syncing", which `exec` continues on; `_sync_flush` now returns 2 for `halted`, `erroring` and `unknown`. (b) `connect` says plainly that it cannot recover either non-converging state instead of resuming a no-op and printing "Already connected" — resume is for PAUSED sessions. `connect` also refuses to create a session while the daemon is unaskable, which could otherwise have made a second session for a profile that already had one. A THIRD fail-open was found by the same review, in the consumer rather than the classifier: `cmd_exec` gated its whole flush block on `_has_sync`, a BOOLEAN that cannot carry "I could not find out", so an unaskable daemon skipped the flush and ran the command with no warning — the most permissive path taken for the least established state. `exec` now refuses on `unknown` and names `--no-flush` as the deliberate escape. SKILL.md's claim that a breaker halt shows as `sync=paused` was false and is corrected — that recovery path never fired

Three test-design errors were caught by mutation runs and are recorded because each is the same trap: the first REMOTE_DIR check tested `$(…)`, which `'…'` already blocked, so it passed with the fix reverted; `_ssh`'s capture-to-variable stub read empty inside `_slurm_submit`'s command substitution, which would have read as "nothing was sent"; and the log-id check was passing because `load_config` died on an empty `RT_CONF` before ever reaching the validator — sourcing `rt` never runs `_init_profile`

- [fixed remote-toolkit@d2305f8] 2026-08-02 **`status --all` enumerated state directories, not configured profiles**, so a configured-but-never-connected profile was invisible — exactly when you would run it to find out what exists, and the `remote` SKILL's first instruction is to run this command to enumerate profiles. Now walks `<host>/*.conf` and unions in any state dir that has no config (a profile whose `.conf` was deleted while connected is still syncing; dropping it would reproduce this defect one directory over), marks that case, and prints the count and the directory it looked in — a bare row list cannot say whether "not listed" means "does not exist" or "not looked for". A directory that is not a valid host-group segment (`_archive/`) is skipped by the same rule that validates `-p`, not by a name list. Config identity is read in a SUBSHELL: configs are sourced bash, so reading eleven in one shell would leak each one's vars into the next and a profile that omits `REMOTE_DIR` would display the previous profile's. **NUMBER CORRECTION**: the 2026-08-02 record said "11 profile config files, 4 shown". Re-derived 2026-08-05 on the same machine: **11 configs, 10 state dirs, 1 invisible** — the defect reproduces, the magnitude does not

- [fixed remote-toolkit@72d44fa] 2026-08-02 **documented sync scope was materially wider than the implementation.** The defaults ignore `outputs/`, `checkpoints/`, `wandb/` and others; the docs said files sync to and from the remote and never enumerated the exclusions, so a result written to any of those paths never became part of the local replica and nothing said why. The default set is now enumerated in both SKILL.md and README.md, next to the three consequences that cost the time — and a canary iterates the code's own `RT_DEFAULT_IGNORES` array against both documents, so a pattern added to `rt` alone now FAILS the suite rather than silently widening the gap this entry is about (with a positive fixture proving that check can still fire). `rt sync status` prints the **live** session's effective ignores via `--template`, not the profile's current text, and — the case that actually bites — DIFFS the two and names the patterns that exist in only one, because Mutagen freezes ignores at session-CREATE time, so editing `MUTAGEN_IGNORE` changes nothing about a running session while making the config file wrong about what is excluded. ### The design note this lane produced

The standing claim in the harness register — *"Mutagen is being used as a job-control protocol:
eventual bidirectional sync decides which code a GPU job launches and which result is
authoritative"* — was put to the de-correlated reader as a question, and came back **TRUE with one
qualification**: ignored result paths are remote-only rather than bidirectionally authoritative,
and under the default mode the LOCAL side wins every conflict, so a local edit can overwrite a
remote result regardless of which was written later.

Its recommended smallest incision, recorded here rather than acted on: a per-run staging wrapper
around `exec --bg` and `slurm submit` — copy a deterministic input snapshot to a unique remote run
directory, verify its manifest digest, launch THERE, write outputs there, and fetch them with a
verified manifest. Mutagen stays a browsing convenience and stops being the correctness boundary.
That is a design change to a shared tool and belongs to a human.
