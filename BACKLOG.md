- A synced tree lands on the remote with Mutagen's portable defaults (files 0600, directories and executables 0700), so a remote process running as another uid gets EACCES → an opt-in per-profile default file and directory mode at session create, documented beside the note that session options freeze at create (2026-10-18).
- The first apply of a small changed file can fail on the remote with `unable to set staged file permissions … no such file or directory` and stay stuck in staging (four times on one profile; flush and pause/resume did not clear it) → find what removes the beta staging file between stage and apply; until then, compare the remote digest before launching (2026-10-11).
- Nothing proves a remote copy equals the local tree before a launch that does not go through `rt`: new files took 30-60 s to arrive (flush gave up at its 10 s default while the session was still applying), and a live edit synced in under a running read-only analysis and broke its imports → an `rt` digest check (local vs remote sha256 for named paths, exit non-zero on a difference) for launchers to call, and a note that long reads import from a frozen copy (2026-10-19, two incidents in one research project).

- [open] id: remote-toolkit#push-new-file-mode-write-only 2026-10-22 lat-surplus: **`rt push` of a NEW file sets its remote mode to `--w------T` (owner write-only + sticky) — unreadable even by the owner — while the local file is 0644 and the remote umask 022; a push that REPLACES an existing file keeps that file's mode (so the defect only shows on first pushes). Four JSON files (three mask specs, one donor spec) sat unreadable for 8 h; the Slurm job that read one died on PermissionError after two of its five stages had run; content digests were fine.** Likely the mode is taken from a decimal `stat` string and applied as octal (0644 dec = 0o1204; observed 0o1200 ≈ 640 dec → `--w------T`) → fix: parse the local mode as octal and apply it masked by the remote umask; `rt push` should `stat` the result and refuse a mode without owner read. Workaround: `chmod 644` on the host after every first push, then `stat -c %A`.
  repro: `rt -p <host>/<profile> push ./new.json dir/new.json` where dir/new.json does not exist; `rt exec 'stat -c %A dir/new.json'` → `--w------T`.

- [open] id: remote-toolkit#recreate-resolves-conflicts-to-stale-local 2026-10-18 lat-surplus: **the documented recipe for applying an ignore change — `rt disconnect && rt connect` — recreates the session with no common ancestor, so any file that differs between the two sides is a conflict, and the default `two-way-resolved` mode hands every conflict to the LOCAL side.** Measured: a job's log had finished on the host (5 KB) while the local replica still held the 185-byte copy from before the disconnect; the recreate overwrote the host's file with the stale copy, silently, exit 0 (the content had been read already, so nothing was lost this time). Any remote-written file that exists on both sides is exposed: slurm logs, results files, run metadata — exactly the files a project recreates a session to protect. SKILL.md now says so beside the recipe (2026-10-18). → next (code): before `_sync_create` on a non-empty local replica, compare the two trees (remote `find -newer` against the local copies, or hashes of the files present on both sides) and refuse or warn naming the files the recreate would overwrite; or create the first session of a recreate in `one-way-safe` from beta and flip to two-way after the first cycle. Which of the two is a behaviour choice for the owner.
  repro: connect a profile; let the host append to a file that is also present locally; `rt disconnect`; `rt connect`; the host's file now has the local content.

- [fixed remote-toolkit@2249020] id: remote-toolkit#scalar-ignore-is-one-pattern 2026-10-18 lat-surplus: **a profile whose `MUTAGEN_IGNORE` was written as a space-separated STRING reached Mutagen as ONE pattern containing spaces, so every ignore in it was silently dead** — the sync began pulling a 24k-file / 7.3 GB conda env from the host to the laptop, and `rt sync status` printed the whole string on one line as if it were a pattern (the only tell). The documented form is a bash array; nothing rejected or split the scalar, and the scalar spelling had already been copied between profiles on one machine (two sibling profiles carry it). Fix: `_ignore_patterns` splits a scalar on whitespace via `read -r -a` (globs stay literal; the array form unchanged); canaries 11g/11h; SKILL.md/README.md name both forms. **Residual exposure:** a LIVE session created from the scalar form still enforces the dead pattern until `rt disconnect && rt connect` — the owner of each such profile recreates it at a quiet moment (the session is mid-run on this machine). The entry-count breaker would have fired only at 50k entries; this env was 24k, so the breaker is not a substitute for the fix.
